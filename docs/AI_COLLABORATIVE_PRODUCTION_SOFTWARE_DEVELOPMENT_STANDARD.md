## 0. AI実行時の最優先規則

AIが本書を参照して開発する場合、最初にこの節を読み、詳細は参照先の節で確認する。この節は要約であり、適用法、契約、組織方針、承認済み製品仕様を上書きしない。

1. **編集前に調査する**: Context Package、対象コード、既存試験、未commit差分を読む。読んでいない対象を推測で変更しない。
2. **事実と推論を分ける**: FACT、ASSUMPTION、DECISION、PROPOSAL、QUESTION、EVIDENCEを混同しない。
3. **正本の衝突を隠さない**: 仕様、コード、試験、実挙動が異なる場合は実装で整合させず、衝突を提示して決定を待つ。
4. **リスクを先に分類する**: R0～R3を決め、該当Levelの承認とEvidenceを満たす。AI単独でLevelを下げない。
5. **推測禁止領域を決めない**: 公開契約、永続化、Security、Privacy、課金、UX、性能閾値、互換性、本番操作は承認済みDECISIONなしに確定しない。
6. **契約を実装より先に確定する**: 観測可能な結果、不変条件、禁止状態、失敗・取消・再開、合否oracleを定義する。
7. **所有者を一つにする**: 同じ状態、データ、資源を複数機能が最終決定しない。状態変更は単一調停経路を通す。
8. **最小差分で実装する**: 一つの目的、一つの所有境界、単独rollback可能な変更にする。無関係な修正を混ぜない。
9. **自己申告を証拠にしない**: source inspection、compile、unit、integration、E2E、人間受入、本番観測を区別し、実行していない検証をPASSとしない。
10. **完了時に知識を戻す**: 要求、ADR、状態、不変条件、試験、Runbook、変更履歴、残存リスクを更新する。

いずれかを満たせない場合、結果を `BLOCKED` または `PARTIALLY VERIFIED` とし、完了や出荷可能と表現しない。この規則が必要な背景は、AIが欠けた文脈を自然な文章で補完し、その補完を事実のように扱えるためである。開発速度より、誤った前提を早期に露出させることを優先する。

## 1. 文書の目的

本書は、MorrowgearのMinecraft Mod開発で実際に行った要求整理、段階実装、状態遷移の再設計、自動試験、実ゲーム検証、目視評価、配布物差し替え、障害分析を、一般の量産ソフトウェア開発へ適用できる標準プロセスとして再構成したものである。

対象はWebサービス、業務システム、モバイル・デスクトップアプリ、ゲーム、組み込み、分散システムを想定する。ただし、法規制、安全性、個人情報、金銭、医療、車載などR3条件を含む領域では、本書を最低線とし、適用規格、Accountable role、要求される独立検証をPhase 0で追加する。

| AIへ実装を任せる | 0、1.3～1.7、6.13 | 6.5～6.10、6.14～6.20 |
| 要求・設計を作る | 4、Phase 1～3 | 6.14～6.19 |

本書では根拠の種類を次のように区別する。

| 表記 | 意味 |
|---|---|
| **実証** | Morrowgearのコード、試験結果、ゲーム内検証で確認した事項 |

| **要調整** | 製品のリスク、組織、法令、利用者に応じて決める事項 |

### 1.1 本書の規範語

本書をAIの参照資料として使う場合、次の語を厳密に解釈する。

| 語 | 意味 | 未達時の扱い |
|---|---|---|
| **MUST / 必須** | 例外なく満たす。法令・製品方針と衝突する場合は作業を停止する | 完了扱いにしない |
| **MUST NOT / 禁止** | 実施してはならない | 実施前に停止し、違反時は変更を隔離する |
| **SHOULD / 原則必須** | 通常は満たす。外す場合は理由、代替統制、承認者、期限をADRへ残す | 無言で省略しない |
| **MAY / 任意** | 目的と費用対効果が合う場合に選択できる | 実施しなくても不適合ではない |

「適切に」「十分に」「必要に応じて」「できるだけ」「高品質に」など、合否を一意に判定できない語は、それだけでAIへの指示として使用してはならない。数値、条件、責任者、証拠、または下記リスク分類へ展開する。

### 1.2 情報の分類

AIは、読み取った情報と自分の推論を混ぜてはならない。作業記録では各事項を次のいずれかに分類する。

| 分類 | 定義 | 例 |
|---|---|---|
| **FACT** | ソース、実行結果、承認記録から直接確認できる | 現行テスト結果は1753件成功 |
| **ASSUMPTION** | 作業継続のために仮置きした未確認事項 | 対応ブラウザは現行最新版のみと仮定 |
| **DECISION** | 権限を持つ人または承認済みADRが選択した事項 | 永続IDは変更しない |
| **PROPOSAL** | AIまたは担当者が提示した未承認案 | retry上限を3回にする案 |
| **QUESTION** | 回答がなければ契約を確定できない事項 | timeout時に利用者へ再試行を促すか |
| **EVIDENCE** | FACTまたは合否を裏付ける再確認可能な証拠 | テストXML、動画、ログ、成果物hash |

ASSUMPTIONとPROPOSALをFACTまたはDECISIONとして扱うことを禁止する。仮定のまま実装可能なのは、後述の「限定的に推測可能な領域」だけである。

### 1.3 正本と優先順位

単一の順位だけですべてを決めない。情報の用途ごとに正本を定める。

| 用途 | 第一の正本 | 補助証拠 |
|---|---|---|
| 法令・契約・セキュリティ制約 | 適用法、契約、承認済み組織方針 | セキュリティレビュー、監査記録 |
| 期待する製品挙動 | 最新の承認済み要求、受入条件、ADR | UX仕様、API仕様、利用者決定記録 |
| 現在実際に起きる挙動 | 実行中システム、現行コード、永続データ | ログ、trace、再現動画 |
| 検証範囲 | 試験仕様と試験コード | 実行結果、coverage、mutation結果 |
| 配布物の内容 | ビルドprovenance、SBOM、成果物hash | ソースrevision、署名 |

コードが動いている事実は「望ましい仕様」を意味しない。試験が成功する事実は「試験の期待値が正しい」ことを意味しない。文書、コード、試験、実挙動が衝突した場合、AIは多数決や新しそうなものを選ばず、次を報告して作業を停止する。

1. 衝突している情報と位置
2. 各情報が示す挙動
3. 利用者、互換性、データ、安全性への影響
4. 選択肢と各選択肢の移行方法
5. 決定権限を持つ承認者

### 1.4 AIによる推測の禁止領域

次は明示的なDECISIONまたは既存の承認済み規則がない限り、AIが決めてはならない。

- 公開API、保存形式、永続ID、通信protocolの互換性
- データ削除、破壊的移行、復元不能な操作
- 認証、認可、暗号、秘密、個人情報、監査要件
- 課金、金額、利用規約、法務、ライセンス、知的財産
- 対応OS、端末、バージョン、ブラウザ、外部サービスの下限
- 性能、可用性、RTO、RPO、容量、費用の合格閾値
- 利用者に見える文言、操作、通知、初期値、ブランド表現
- 複数の妥当な業務解釈がある状態遷移と優先順位
- 本番配備、Feature flag公開、rollback、障害時の利用者通知
- 安全性に影響するrisk、またはSecurity ownerがR3に分類したriskの受容

これらが未確定でも、調査、選択肢作成、prototype、破棄可能な試験コードまでは実施できる。ただし本番コード、永続データ、公開契約へ反映してはならない。

### 1.5 限定的に推測可能な領域

AIは、次の条件をすべて満たす場合だけ、既存パターンから実装詳細を補完できる。

1. 外部から観測可能な挙動を変えない。
2. 永続データ、公開契約、権限、安全性へ影響しない。
3. リポジトリ内に一貫した既存パターンが二例以上ある。
4. 変更を単独で元に戻せる。
5. 自動試験で補完結果を検証できる。
6. 採用したパターンと参照箇所を作業報告へ記録する。

例として、既存formatterに従う整形、非公開の局所変数名、既存factoryを用いたtest fixture作成は該当し得る。公開文言、初期値、timeout、retry回数、業務ルールは該当しない。

### 1.6 作業停止条件

AIは次のいずれかを検出した時点で、変更を拡大せず、進捗、証拠、未確定事項を報告する。

- 正本同士の矛盾または要求と試験の矛盾
- 推測禁止領域に必要なDECISIONの欠落
- 予定外の破壊的変更、データ損失、権限拡大の可能性
- 秘密情報、個人情報、ライセンス不明素材の混入
- 変更対象に、AIが作成していない未理解の差分がある
- 必須試験を実行できない、または合否oracleを定義できない
- 変更範囲が承認済み対象を越えた
- rollbackまたは安全な失敗状態がないR3変更
- 同じ失敗を原因不明のまま三回以上繰り返した
- 実行証拠なしに完了を主張する必要が生じた

停止は失敗ではない。不確実性を隠して実装を続けることが不適合である。

### 1.7 変更リスク分類

AIが「高リスク」を感覚で判断しないよう、変更開始時に次の最高該当レベルを付ける。

| Level | 条件 | 最低限必要な統制 |
|---|---|---|
| **R0** | 文書、コメント、生成物のみ。実行挙動を変えない | 差分確認、リンク・形式検証 |
| **R1** | 単一module内の可逆な内部変更。公開契約、永続化、権限、並行性へ影響しない | 単体試験、静的検査、担当者レビュー |
| **R2** | 利用者向け挙動、API、状態遷移、並行処理、性能、外部I/O、後方互換なschema変更 | R1 + 契約/結合/E2E、影響回帰、rollback確認、別視点レビュー |
| **R3** | 認証・認可、秘密、個人情報、課金、破壊的移行、不可逆操作、安全、広域障害、本番基盤 | R2 + threat model、該当Accountable roleによる承認、段階展開、復旧演習、監査証跡 |

複数条件に該当する場合は最も高いLevelを使う。リスクを下げる場合は、理由と代替統制を承認済みADRに残す。AI単独でLevelを下げてはならない。

### 1.8 曖昧語の判定可能な定義

| 曖昧語 | 本書での意味 |
|---|---|
| **重要要求** | R2/R3に関係する要求、またはProduct ownerがCritical指定した要求 |
| **小さな変更** | 一つの観測可能な目的だけを持ち、一つの所有境界内で、単独rollbackでき、レビュー者が差分と試験を一回で追跡できる変更 |
| **本番に近い環境** | `ENVIRONMENT_CONTRACT`に列挙したruntime、build tool、OS/architecture、schema、認証・権限semantics、依存protocolのversionを本番と一致させ、対象NFRに記載したデータ量・遅延・障害条件を再現する環境。意図的な差異は影響と代替統制を記録する |
| **十分な証拠** | 要求ID、実行条件、期待値、実測値、結果、時刻、成果物version、未確認範囲を含み、第三者が再確認できる証拠 |
| **独立検証** | 実装結果の説明をoracleにせず、承認済み契約から別担当・別context・自動化された判定器が合否を評価すること |
| **完了** | 必須Gateを満たし、未確認事項と残存リスクが承認され、配布または引渡し可能な状態。コードを書き終えただけでは完了ではない |
| **Safe state** | 追加のデータ破損、権限逸脱、課金、安全被害、外部副作用を発生させず、観測と復旧が可能な状態。製品ごとに状態名、許可操作、復旧手順をSTATE_MODELとRUNBOOKへ記載する |
| **長時間試験** | NFRで定義した最大連続稼働時間、resource leak検出窓、周期処理の最長周期のうち最大の時間を実時間または仮想時刻で通過させる試験。時間が未定義なら試験時間をAIが決めずQUESTIONとする |
| **最大負荷** | 容量計画で承認された同時利用数、request/event rate、data volume、queue depth、resource上限の組。値がない状態で「最大」を名乗らない |

### 1.9 故障重大度

変更リスクは「変更が持つ危険」、故障重大度は「実際に故障した場合の最大影響」であり、別々に評価する。

| Severity | 最大影響 | 必須対応 |
|---|---|---|
| **S0** | 利用者から観測不能。内部診断だけに影響 | 通常の修正・回帰 |
| **S1** | 限定利用者の非主要機能が一時劣化し、データ・権限・課金に影響しない | issue記録、対象回帰、release判断 |
| **S2** | 主要操作不能、広範な性能劣化、回復可能な不整合、手動介入が必要 | 封じ込め、原因分析、回帰追加、Product/Service owner承認 |
| **S3** | データ損失、Security/Privacy侵害、誤課金、安全被害、復旧不能、広域停止 | 即時停止・rollback、incident対応、該当専門Role承認、事後分析 |

故障モードのSeverityは「通常想定する影響」ではなく、既存統制が失敗した場合の合理的な最大影響で決める。AIは証拠なしにSeverityを下げない。

## 2. 結論

量産開発へ移植すべき中核は、「AIに大量に作らせること」ではなく、次の制御されたフィードバックループである。

1. 利用者が期待する観測可能な挙動を契約として定義する。
2. 状態、データ、識別子、資源、判断権限の所有者を一つに定める。
3. 変更を小さく実装し、影響範囲に応じた試験を自動実行する。
4. 自動試験で証明できない実環境・UI・音・操作感・復旧性を実機で検証する。
5. 配布物、設定、データを安全かつ追跡可能に更新する。
6. 本番の観測結果と障害から、要求・設計・試験へ知識を戻す。

AIは探索、候補生成、実装、試験列挙、解析、文書化を高速化できる。一方、事業目的、許容リスク、曖昧な要求の確定、セキュリティ例外、破壊的変更、法的判断、最終的な使いやすさ、出荷可否は人間が責任を持つ。したがって目標は **AI-firstではなくAI-assisted、AI-onlyではなくevidence-driven** である。

## 3. Morrowgearで得た一般化可能な知見

| Morrowgearでの事象 | 一般ソフトウェアへの対応 |
|---|---|
| ドローンの見た目・速度・任務復帰を実ゲームで確認 | ユーザー受入試験、実機試験、探索的試験 |
| 状態遷移が複数処理から上書きされ挙動が不安定化 | 単一の状態調停者、明示的優先順位、状態機械 |
| Wing、cohort、missionの境界混同 | 永続ID、業務集約、実行単位、一時単位の分離 |
| 任務中断後に対象が消えて復帰不能 | 中断可能処理、再開前の前提再検証、フォールバック |
| 充電・帰還・戦闘の競合 | 資源予約、優先度付きキュー、排他、冪等性 |
| 1753件のJUnit試験とゲーム内検証器 | 単体試験とシステム試験を分け、証明範囲を明記 |
| UI、音、レーザーは自動試験だけでは判定不能 | 視覚・聴覚・人間工学の評価を独立ゲート化 |
| 試験場や前ケースの状態が次ケースを汚染 | テスト分離、決定的fixture、後始末、再現性 |
| JARを一時ファイル経由で差し替え | 原子的配備、ロールバック可能なリリース |
| アップデート後も既存機体・Dockを維持 | スキーマ移行、後方互換、永続ID不変 |
| スコープ別ゲーム内検証 | リスクベース回帰試験と対象限定の高速確認 |
| HUDと検証ログで内部状態を可視化 | 構造化ログ、メトリクス、トレース、意思決定ログ |

重要なのは試験数ではない。1753件が成功していても、それだけではMinecraft上の描画、音、操作感、NFRで定義した連続稼働時間の挙動を証明しない。各試験が何を証明し、何を証明しないかを明示して初めて品質証拠になる。

## 4. 開発を支える原則

### 4.1 観測可能な契約を先に置く

要求は「高速」「使いやすい」「安全」のような形容詞で終えず、入力、前提、操作、期待出力、時間、失敗時の挙動、保持すべき不変条件で記述する。

例:

- 悪い要求: 「充電後に正しく復帰する」
- 良い要求: 「任務中に電力が閾値未満になった機体は任務コンテキストを保存してDockへ移動し、出撃可能条件を満たした時点で、対象と任務が有効なら復帰し、無効なら定義済みフォールバックへ遷移する」

完了条件はコード変更ではなく、利用者または外部システムから確認可能な結果と証拠で定める。

### 4.2 所有権を一つにする

同じ値や状態を複数の処理が独立に決めると、局所的には正しくても全体が振動する。少なくとも次を明示する。

- 状態遷移を最終決定する所有者
- 永続データの正本
- リーダー選出・資源予約・再試行の決定者
- UI表示値の出典
- 障害時に縮退・停止を決める責任主体

複雑な制御は `要求状態 -> 調停 -> 許可済み状態 -> 物理/実処理` の順にし、各機能が直接最終状態を書き換えない。

### 4.3 不変条件を設計の中心に置く

機能ごとの期待値に加え、どの状態でも破ってはならない条件を定義する。

- IDは更新後も変わらない。
- 同じ資源を二重予約しない。
- 完了・取消済みの仕事は再開しない。
- 所有者の異なるグループへ勝手に参加しない。
- 同じ要求を再送しても二重実行しない。
- 中断処理は元の処理を失わず、再開時に前提を再確認する。
- 失敗してもデータを部分更新状態にしない。

### 4.4 品質はリスクで配分する

すべてを同じ深さで試験しない。変更の影響、回復困難性、利用頻度、セキュリティ、金銭・データ損失、人命・法規制を基に試験深度と承認者を決める。一方、テスト件数やコードカバレッジだけを品質指標にしない。

### 4.5 証拠を変更と一緒に残す

要求ID、設計判断、変更差分、自動試験、実機証拠、既知制約、配布物ハッシュ、ロールバック手順を同じ変更単位に関連付ける。後から「なぜ安全と判断したか」を再構成できることが量産品質である。

### 4.6 不正な状態を表現できなくする

バグを減らす最も強い方法は、開発者やAIが注意深く実装することだけに頼らず、型、データ構造、APIによって誤りを作れなくすることである。

複数のbooleanで排他的状態を表現しない。

```text
危険: isDocked=true, isAttacking=true, isReturning=true

推奨: OperationalState =
  Docked
  Navigating
  Combat
  ReturningToService
  PowerLost
```

状態ごとに必要な情報が違う場合は、その情報も状態へ含める。例えば `Combat(targetId, engagementId)` と `ReturningToService(dockId, suspendedMission)` を分ければ、攻撃対象のないCombatや帰還先のないReturning状態を作りにくくできる。

同じ原則を次にも適用する。

- 検証済み入力と未検証入力を別の型にする。
- 永続ID、一時ID、表示名を別の型にする。
- 金額、距離、期間、割合、座標の単位を型または値オブジェクトで保持する。
- 成功、再試行可能な失敗、永続的失敗、取消を同じnullや例外で表さない。
- 未初期化、処理中、利用可能、廃止済みを明示する。

### 4.7 判断権限を単一の調停器へ集約する

追従、戦闘、充電、復旧など複数機能が最終状態を直接変更してはならない。各機能は要求を提出し、単一の調停器が優先順位、不変条件、現在の資源、既存の予約を評価して決定する。

```text
状態要求群
  CombatRequest
  ServiceRequest
  MissionRequest
  RecoveryRequest
        ↓
Operational Arbiter
        ↓
許可済みの次状態 + 実行Command
```

調停規則は散在するif文ではなく、優先順位表または遷移表として管理する。同順位の場合の決定方法、preemptionの可否、処理完了後の復帰先も定義する。

### 4.8 判断と副作用を分離する

中核判断は、同じ入力に対して同じ結果を返す純粋なDecision Coreとして実装する。

```text
decide(currentState, events, resources, policy)
  -> nextState, commands, decisionReason
```

移動、DB更新、ネットワーク、ファイル、描画、通知などはEffect AdapterがCommandを実行する。これにより、状態判断をゲーム、DB、ネットワークなしで高速かつ決定的に試験できる。副作用が失敗した場合は、成功したと仮定して状態を進めず、再試行・補償・停止のいずれかへ遷移する。

### 4.9 中断・再開・取消を通常系として設計する

中断は例外ではなく量産システムの通常動作である。割込み時には、少なくとも元の任務、進捗、再開条件、取得資源、期限、重複防止IDを保存する。

再開時には中断前の状態へ無条件に戻さず、次を再評価する。

- 対象が存在し、同一の対象であるか。
- 利用者または上位処理が取消していないか。
- 権限、所有権、期限、資源がまだ有効か。
- 他処理が目的を既に達成していないか。
- 再開より安全な代替処理がないか。

再開できない場合の結果を `complete`、`retarget`、`requeue`、`fallback`、`abort` に分類し、単なる待機状態へ落として仕事を失わない。

### 4.10 不変条件を実行可能にする

設計書に書くだけでなく、assertion、検証関数、DB制約、型制約、監視ルールとして実行する。

```text
invariant:
  unit belongs to at most one persistent group
  resource has at most one active reservation
  completed work is never resumed
  power-lost unit cannot receive flight commands
  persistent identity never changes during upgrade
```

不変条件は単体試験だけでなく、状態遷移の直後、永続化の前後、E2E試験の終了時、本番監視でも検査する。違反時は自動修復を無条件に試みず、証拠を残して製品ごとに定義したSafe stateへ停止または縮退する。

### 4.11 時間・乱数・外部環境を依存として扱う

現在時刻、乱数、ファイル、ネットワーク、OS、ゲーム世界を中核ロジックから直接参照しない。Clock、Random、Repository、Gateway等として注入し、試験では仮想時刻、固定seed、制御可能な失敗を使う。

これにより、数時間後のtimeout、順序逆転、retry、資源枯渇、長時間運転を短時間で再現できる。非決定性が必要な機能でも、使用したseedとイベント列を記録して再現可能にする。

### 4.12 失敗時に収束する設計にする

失敗時に「もう一度試す」だけではなく、有限回で安全な状態へ収束することを設計する。

- 冪等性keyで重複実行を防ぐ。
- retry回数、deadline、backoff、jitterを定義する。
- 資源予約にleaseと期限を設ける。
- 部分成功にはtransactionまたは補償処理を用意する。
- キューへ戻す前に仕事の有効性を再確認する。
- 復旧不能時はdead-letter、手動介入、明示的失敗へ送る。
- 同じ二状態を高速に往復する振動を検出し、cooldownまたはhysteresisを使う。

設計完了の条件は「正常系が動く」ではなく、Critical要求またはR2/R3変更に関係するすべての処理が、成功、失敗、取消、timeout、再起動のいずれでも定義済みの終端へ到達することである。

### 4.13 設計規則が必要な理由

AIは規則の目的を理解しないと、表面的に従いながら別の場所で同じ危険を再導入する。設計レビューでは、規則、背景、防ぐ不具合、証拠をセットで扱う。

| 規則 | 背景 | 主に防ぐ不具合 | 必要な証拠 |
|---|---|---|---|
| 不正状態を表現不能にする | booleanやnullの組合せ数は機能追加と共に急増する | 矛盾状態、初期化漏れ、分岐漏れ | 型定義、constructor制約、禁止状態test |
| 単一調停器を使う | 複数機能が同じ状態を直接上書きすると最終決定者が不明になる | 状態振動、優先度逆転、任務消失 | 遷移表、単一entry point、競合test |
| 判断と副作用を分ける | 外部I/Oを含む判断は遅く、非決定的で、失敗途中を再現しにくい | 再現不能、部分更新、mock依存 | pure decision test、adapter結合test |
| 不変条件を実行する | 文書だけの規則は変更時に自動検知されない | group重複、二重予約、ID変化 | constraint、assertion、property test、監視 |
| 中断・再開を通常系にする | 長い処理では対象・権限・期限が途中で変わる | stale task、終了済み仕事の復活、待機落ち | interruption/resume/target-loss test |
| 時間・乱数を注入する | wall clockや非固定乱数は同じ障害を再現できない | flaky、timeout境界漏れ、順序依存 | virtual clock、seed記録、再現test |
| 有限回で収束させる | 無制限retryや相互preemptionは処理を終わらせない | retry storm、livelock、資源枯渇 | 上限、deadline、終端到達test、運用metric |
| 原子的更新と冪等性 | 実行途中の停止と要求再送は通常発生する | 二重処理、半端なデータ、復旧不能 | transaction/idempotency/crash-recovery test |

「規則を実装した」という説明だけでは合格にしない。表の右端にある証拠が得られない場合、設計上の狙いを達成したとは判定しない。

### 4.14 整合性境界と原子的変更を定義する

永続化を伴うR2/R3変更では、AIは処理単位をコードの関数境界から推測してはならない。`DATA_AND_API.md`に、次を承認済み契約として記録する。

- 同時に成功または失敗しなければならないデータを一つの整合性境界として列挙する。
- 境界内の正本、書込み所有者、transaction開始・commit地点を一つにする。
- 境界をまたぐ更新は、強整合性、結果整合性、補償処理のどれを採用するかと、利用者が観測できる中間状態を定義する。
- 状態更新とevent発行を別々に行う場合は、transactional outbox等の原子性を保証する方式、重複排除、再送、配信不能時の扱いを定義する。
- 削除は物理削除、論理削除、tombstoneのどれかを決め、参照、再作成、保持期間、監査、個人情報削除との関係を定義する。

外部システムを含み単一transactionにできない処理は「ほぼ同時だから成功」と扱わない。各stepの成功記録、再実行条件、補償の順序、補償も失敗した場合のSafe stateと運用介入を契約に含める。

### 4.15 並行更新とevent順序を契約化する

共有状態へ複数のwriterが到達し得る場合、次を未定義のまま実装へ進まない。

- 排他、optimistic concurrency、compare-and-set、single writer、queue直列化のいずれで競合を制御するか。
- version、sequence、idempotency key、correlation IDの生成者と有効範囲。
- lost updateを検出した際に、再読込して再評価するか、利用者へ競合を返すか、処理を破棄するか。
- eventの順序保証範囲、重複、欠落、遅延、再配信、古いeventの扱い。
- lease、lock、reservationの期限、更新、所有者喪失、process停止後の解放方法。

retryは同じ判断結果の再送とは限らない。再試行前に対象version、権限、期限、要求の有効性を再評価する。競合解決をlast-write-winsにする場合は、失われてもよい情報とその製品上の根拠をDECISIONとして残す。

### 4.16 データ・API・eventを段階的に進化させる

公開契約または永続データの変更では、旧reader、新reader、旧writer、新writerが共存する期間を想定する。少なくとも次を定義する。

- 互換性の方向。後方、前方、双方向、非互換のいずれか。
- add、backfill、read切替、write切替、削除からなるexpand-contractの順序。
- 未知field、欠落field、enum追加、default、単位変更、精度変更へのreaderの挙動。
- migrationの再実行性、途中再開、件数照合、checksum、所要時間、失敗時の戻し方。
- rollback時に新versionが書いたデータを旧versionが読める条件。読めない場合はroll-forwardを正式な復旧方法とする根拠。
- 永続ID、外部ID、表示名の不変範囲と、merge、split、削除、再作成時の規則。

SemVerの版番号だけを移行設計の証拠にしてはならない。実データfixtureを使い、対応するすべてのversion組合せでreader/writer契約を検証する。

### 4.17 resource・取消・停止の寿命を揃える

thread、task、connection、file、lock、lease、subscription、GPU/OS resource等は、取得主体と解放主体を明示する。親処理の取消、deadline、process停止は子処理へ伝播させ、完了済み処理へ遅れて届いたcallbackが状態を復活させないようgenerationまたはversionを検証する。

停止順序は「新規受付停止、処理中作業のdrainまたは取消、永続化完了、event送出確認、resource解放、停止完了」のどこまでを保証するか定義する。強制停止を含む場合は、再起動時に未完了作業を識別して再評価できる証拠を残す。

## 5. 標準ライフサイクル

### Phase 0: 事業・ガバナンス

**理由**: 目的と許容リスクが未定義だと、AIは技術的に作りやすいものを最適化し、利用者価値、法令、運用費用を代わりに決めてしまう。このPhaseは、技術判断の外側にある人間の決定を固定するために必要である。

**入力**: 課題、利用者、制約、予算、法規制、既存資産

**実施**:

- 利用者価値と成功指標を定義する。
- 製品のリスク階級、データ分類、可用性要求を決める。
- Product、開発、QA、Security、運用、UXの責任者を置く。
- AIへ入力してよい情報、利用可能ツール、承認境界を定める。
- 開発・運用・廃止までの費用を見積もる。

**成果物**: Product brief、リスク台帳、責任分担、AI利用方針

**Gate 0**: 誰の何を改善し、どの危険を許容しないか説明できる。

### Phase 1: 発見・要求定義

**理由**: 同じ機能名でも利用者が期待する入力、完了、失敗時挙動は異なる。受入条件がなければ、AIは実装しやすい挙動を仕様として固定し、試験もその実装を追認する形になる。

**実施**:

- 現状業務、利用シナリオ、競合、失敗時の影響を調査する。
- 正常、境界、異常、取消、中断、再開、更新、廃止を列挙する。
- 機能要件と非機能要件を分ける。
- 性能、可用性、復旧、セキュリティ、プライバシー、互換性、アクセシビリティ、保守性を数値化する。
- 要求ごとに受入条件と観測方法を定義する。

**成果物**: 要求仕様、ユースケース、NFR、要求・試験トレーサビリティ表

**Gate 1**: 重要要求に一意なID、受入条件、検証方法、責任者がある。

### Phase 2: アーキテクチャ・危険分析

**理由**: 局所的に正しいコードを積み重ねても、所有権、並行性、永続化、失敗処理が競合すればシステム全体は不安定になる。実装前に境界と故障時の収束先を定め、変更が守る構造を作る。

**実施**:

- コンテキスト、主要コンポーネント、依存先、信頼境界を図示する。
- 状態、イベント、データ、ID、資源、時間、並行性をモデル化する。
- 整合性境界、transaction、writer、競合制御、event順序、ID寿命を定義する。
- 旧版と新版の共存、migration、rollbackまたはroll-forwardの成立条件を定義する。
- 脅威モデルと故障モード分析を行う。
- タイムアウト、再試行、キャンセル、冪等性、バックプレッシャー、縮退、停止、復旧を設計する。
- ADRで採用案、却下案、理由、見直し条件を残す。

**成果物**: アーキテクチャ図、状態遷移表、データ/API契約、脅威・故障モデル、ADR

**Gate 2**: 単一障害点、競合する所有者、循環依存、無限再試行、復帰不能状態に加え、原子性、同時更新、event順序、version共存、resource解放が説明・対策されている。

### Phase 3: 試験設計

**理由**: 実装後に試験を書くと、実装した挙動を正しいとみなすconfirmation biasが入りやすい。要求と危険から先にoracleを作り、設計・実装とは独立した失敗条件を固定する。

実装前に、要求と危険から試験を設計する。主要な試験層は次のとおり。

| 層 | 主に証明するもの |
|---|---|
| 静的検査 | 型、規約、既知脆弱性、危険な構文、ライセンス |
| 単体・プロパティ試験 | 純粋ロジック、境界、不変条件 |
| 状態遷移・モデルベース試験 | 遷移、優先順位、割込み、再開、禁止遷移 |
| 契約試験 | API、イベント、スキーマ、他チームとの境界 |
| コンポーネント試験 | DB、キュー、ファイル、外部I/Oを含む単位 |
| 結合試験 | コンポーネント間の実接続、競合、トランザクション |
| システム/E2E試験 | 実行環境での利用者シナリオ |
| 非機能試験 | 性能、負荷、長時間、セキュリティ、回復、互換性 |
| 人間による評価 | UI、音、理解しやすさ、操作感、アクセシビリティ |
| 本番検証 | Canary、synthetic、監視、SLO、ロールバック |

**Gate 3**: 重要要求とS2/S3故障モードに、独立した検証方法と合否基準がある。

### Phase 4: 実装

**理由**: 変更が大きいほど、原因、影響、rollback単位を分離できなくなる。観測可能な目的ごとに差分を限定し、試験・移行・観測を同じ変更へ含めることで、AIが局所修正を連鎖的な再設計へ拡大することを防ぐ。

**実施**:

- 小さくレビュー可能な変更単位にする。
- 既存の所有境界と設計パターンを優先する。
- 外部入力を検証し、秘密情報をコード・ログ・AI入力へ置かない。
- 永続IDや公開契約を不用意に変更しない。
- 変更と同時に試験、観測点、移行、ロールバックを実装する。
- Feature flagやkill switchで危険な機能を切り離せるようにする。

**Gate 4**: 差分が要求へ追跡でき、レビュー、自動試験、セキュリティ検査を通過している。

### Phase 5: 統合・実環境検証

**理由**: mockと純粋ロジックは、実際のversion差、権限、描画、音、性能、データ量、ネットワーク、状態汚染を再現しきれない。自動単体試験の証明範囲を越える部分を、対象環境と人間の知覚で確認する。

**実施**:

- 本番に近い依存関係、データ量、権限、ネットワーク条件で確認する。
- テストごとに環境を初期化し、前ケースの状態を残さない。
- 本番データを無断複製せず、合成データまたは承認済みの匿名化・最小化済みデータを用い、保存先、アクセス権、削除期限を記録する。
- 実際の状態、出力、距離、時間、保存結果を検証し、コマンド成功だけを合格にしない。
- UIは画面サイズ、DPI、データ件数、言語、入力方式を変える。
- NFRで定義した長時間試験と最大負荷に加え、資源枯渇、部分障害、遅延、順序逆転を注入する。NFR値が未定義ならQUESTIONとしてGate 5を通過させない。
- 更新前データでアップグレードし、再起動後の保持とダウングレード可否を確認する。

**Gate 5**: 受入条件を満たす客観証拠と、人間が確認すべき項目の承認が揃っている。

### Phase 6: リリース

**理由**: 正しいコードでも、異なる依存でbuildされた成果物、途中で失敗する配備、互換性のないschema変更により利用者環境を壊せる。ソースから配布物までの追跡性と、失敗しても戻せる更新単位を保証する。

**実施**:

- 再現可能なビルド、依存固定、成果物ハッシュを用いる。
- SBOM、出所情報、署名、脆弱性結果を生成・保管する。
- 保護branchでは要求されたreviewとCI checkを迂回できないようにし、例外は6.12の手続へ従う。
- CIで検証した一つのimmutable artifactを環境間で昇格させ、各環境でソースから別buildしない。
- 配備を原子的にし、途中失敗で半端な状態を残さない。
- DBはexpand-contract等で前後バージョンの共存期間を作る。
- Canary、段階展開、監視付きリリース、即時停止・ロールバックを用意する。
- rollback不能なdata変更では、停止、roll-forward、復元の判断条件と最大復旧時間をリリース前に演習する。
- リリースノート、既知制約、運用手順、移行手順を提供する。

**Gate 6**: 配布物をソースとビルドへ追跡でき、復旧時間内に戻せることを演習済みである。

### Phase 7: 運用・改善

**理由**: 事前試験は本番の全入力、規模、依存障害を網羅できない。承認済みSLIへ対応する利用者結果を継続観測し、未検出の故障を要求・設計・試験へ戻すことで品質loopを閉じる。

**実施**:

- ログ、メトリクス、トレース、ユーザー体験指標を関連付ける。
- SLI/SLOとエラーバジェットを定める。
- 症状、原因候補、意思決定理由、相関IDを観測できるようにする。
- log、metric label、trace attributeごとに個人情報・秘密・監査要件、保存期間、sampling、cardinality上限を定義する。
- アラートは行動可能なものに絞り、重複・警報疲れを防ぐ。
- 各alertに利用者影響、owner、初動、escalation、解除条件を対応させ、通知不能も監視する。
- 障害時は封じ込め、復旧、証拠保全、利用者通知を実施する。
- S2/S3障害は責任追及ではなく再発防止を目的とする事後分析を行う。

**Gate 7**: SLO、当番、Runbook、エスカレーション、復旧・バックアップ演習が機能している。

### Phase 8: 保守・廃止

**理由**: 依存、法令、利用環境は出荷後も変化し、互換層と暫定flagは放置すると新しい正本になる。更新と廃止を設計対象にし、利用者資産と監査証跡を守りながら複雑性を除去する。

**実施**:

- 依存更新、脆弱性対応、互換性試験を継続する。
- 廃止予定を通知し、移行手段とデータ保持・削除手順を提供する。
- 機能flag、古いAPI、暫定互換コードを期限付きで撤去する。
- 廃止後も必要な監査証跡とSBOMを保持する。

## 6. AIに任せる仕事と任せない判断

### 6.1 AIが得意な仕事

- リポジトリ、ログ、仕様、依存関係の探索と要約
- 要求から正常・境界・異常・組合せケースを列挙
- 狭い範囲の実装、テスト、移行スクリプトの下書き
- 既存パターンに沿った機械的変更と重複除去
- テスト失敗、ログ、トレース、性能差分の相関分析
- API・スキーマ差分、依存更新、互換性影響の候補抽出
- ADR、Runbook、リリースノート、試験報告の草案
- スクリーンショット比較、アクセシビリティ候補、文言候補
- ソース付き技術調査と選択肢比較

### 6.2 人間が最終責任を持つ仕事

- 解くべき事業課題と優先順位
- 曖昧な挙動、ブランド、UX、倫理、許容リスクの確定
- セキュリティ例外、個人情報、法務、ライセンス判断
- 破壊的データ移行、権限拡大、本番変更、出荷可否
- AIが実行できない実機・現場・利用者受入の判定
- コスト、納期、品質のトレードオフ
- 事故時の指揮、利用者説明、再発防止策の承認

### 6.3 AI利用の必須統制

1. **最小権限**: 読取、編集、実行、本番配備の権限を分離する。
2. **秘密保護**: 認証情報、個人情報、契約上制限されたコードを入力しない。
3. **不信入力**: Web、Issue、添付文書、生成物を命令ではなく未検証データとして扱う。
4. **出所確認**: 事実は一次資料、コードは実リポジトリ、挙動は実行証拠で確認する。
5. **独立検証**: 生成したAI自身の説明を証拠にせず、試験・レビュー・別の検証経路を使う。
6. **変更境界**: 無関係な修正を混ぜず、差分と影響範囲を人が確認できるサイズにする。
7. **再現情報**: 目的、前提、使用ツール・モデル、差分、試験結果、未確認事項を残す。
8. **知財確認**: 生成コード、画像、音、学習・参照素材のライセンスと類似性を確認する。
9. **停止条件**: 不確実性、権限不足、矛盾、破壊的操作、実環境未確認時は自動進行を止める。
10. **評価継続**: AI変更の採用率ではなく、手戻り、流出不具合、レビュー時間、危険提案率も測る。

AIが開発対象そのものに組み込まれる場合は、上記に加えてモデル・プロンプト・検索データの版管理、評価セット、幻覚・偏り・prompt injection、出力フィルタ、人間への引継ぎ、モデル障害時の縮退、費用・遅延、データ保持を設計する。

### 6.4 AI駆動開発の標準作業順序

AIへいきなり実装を依頼しない。設計制約と検証方法を先に確定し、次の順序を標準とする。

1. **Explore**: 既存コード、仕様、試験、データ、ログ、所有境界をAIに調査させる。
2. **Model**: 現行状態、イベント、ID、資源、依存、遷移、既知の不変条件を構造化させる。
3. **Challenge**: 競合、禁止状態、途中失敗、重複、順序逆転、対象消失、更新影響を反証させる。
4. **Contract**: 変更後の観測可能な契約と合否基準を人間が承認する。
5. **Implement**: AIに最小差分で実装・試験・観測点を同時追加させる。
6. **Verify**: 自動試験、静的検査、実環境試験を独立した証拠として実行する。
7. **Inspect**: 差分、実画面、ログ、性能、移行結果を人間が確認する。
8. **Record**: 判断理由、証拠、未確認事項、残存リスク、ロールバックを記録する。

各段階を同じAIセッションで行ってもよいが、「実装したAIの自己申告」を検証結果として扱わない。高リスク変更では、設計・実装・検証の担当AIまたはcontextを分離し、検証側へ期待する実装詳細を与えすぎない。

### 6.5 AIへ渡す実装タスク契約

AIへの依頼には最低限、次を含める。情報が欠けている場合、AIは推測で公開契約や永続形式を決めず、調査または確認へ戻る。

```text
目的:
利用者から見える期待結果:
対象範囲 / 対象外:
現在の正本と所有者:
入力イベント:
状態と優先順位:
破ってはならない不変条件:
中断・取消・再開・失敗時の挙動:
互換性と移行条件:
性能・セキュリティ・UI制約:
必要な観測情報:
必須試験:
実機で人が確認する項目:
完了証拠:
```

AIは実装前に次を返す。

- 理解した契約と仮定
- 影響を受ける状態、データ、API、試験
- 新たに生じる禁止状態と不変条件
- 最小変更案と代替案
- 失敗時・更新時・ロールバック時の挙動
- 自動化できる検証と、人間に残る検証

実装後は、変更ファイル一覧だけでなく、要求ごとの証拠、未確認事項、残存リスクを報告する。試験を実行していない場合や実機を確認していない場合は、成功したと表現してはならない。

### 6.6 AI Context Packageの必須項目

AIは会話履歴だけを正本にしてはならない。長い会話は省略、要約、古い決定の混在が起きるため、継続開発ではリポジトリ内に次のContext Packageを保持する。

| Artifact | 内容 | 必要な理由 |
|---|---|---|
| `PRODUCT.md` | 利用者、価値、対象外、主要用語 | 技術的に可能な案と製品として正しい案を区別する |
| `REQUIREMENTS.md` | 要求ID、受入条件、優先度、承認状態 | AIが会話から仕様を再構成することを防ぐ |
| `ARCHITECTURE.md` | 境界、依存、正本、trust boundary | 既存所有境界を越えた実装を防ぐ |
| `STATE_MODEL.md` | 状態、event、guard、action、優先度、終端 | 状態追加時の競合と禁止遷移を検出する |
| `INVARIANTS.md` | 不変条件ID、適用範囲、実行検査箇所 | 暗黙ルールの消失を防ぐ |
| `DATA_AND_API.md` | schema、ID、正本、writer、整合性・transaction境界、競合制御、event順序、公開契約、version、移行規則 | 更新で利用者データや連携を壊すことを防ぐ |
| `TEST_STRATEGY.md` | 要求・リスクと試験層の対応 | 件数だけ多く証明範囲が不足することを防ぐ |
| `RUNBOOK.md` | 配備、監視、rollback、復旧、連絡 | 実装者しか直せない状態を防ぐ |
| `ADR/` | 採用案、却下案、理由、見直し条件 | 後続AIが過去の失敗案を再導入することを防ぐ |
| `CHANGELOG.md` | 公開変更、互換性、移行 | 利用者と運用者が変更影響を判断できるようにする |

小規模製品ではファイルを統合してもよいが、各情報の見出しと正本は維持する。Artifactが存在しない場合、AIは現行コードからFACTを抽出し、未確定部分をASSUMPTIONまたはQUESTIONとしてContext Packageの草案を作る。草案が承認されるまで、R2/R3の挙動変更へ進まない。

### 6.7 AIの実装前出力契約

AIはファイル編集前に、次の順序で短い実装前報告を出す。R0で自明な文書修正を除き、省略してはならない。

```text
[TASK]
要求ID / 目的 / リスクLevel

[FACTS]
確認した正本、コード、試験、実行結果

[UNKNOWN]
未確認、矛盾、欠落情報

[IMPACT]
影響する状態、API、データ、UI、Security、運用、互換性

[INVARIANTS]
維持する条件と新たに追加する条件

[PLAN]
変更箇所、変更しない箇所、rollback方法

[VERIFICATION]
要求IDごとの試験、実機確認、合否oracle

[DECISIONS REQUIRED]
人間の決定が必要な項目。なければ NONE
```

目的は説明量を増やすことではなく、実装前に誤った前提を見える形にすることである。UNKNOWNを空に見せるため、推測をFACTへ移してはならない。

### 6.8 AIの実装後出力契約

```text
[RESULT]
COMPLETE / PARTIALLY VERIFIED / BLOCKED / FAILED

[CHANGES]
要求IDと変更箇所の対応

[EVIDENCE]
実行したcommand、試験件数、実測値、画面・log・artifact

[NOT VERIFIED]
実施していない実機、性能、Security、互換性確認

[RESIDUAL RISK]
残る危険、影響、検出方法、回避策

[ROLLBACK]
戻し方と、戻した際に保持・失われるもの

[CONTEXT UPDATES]
更新した仕様、ADR、状態、不変条件、Runbook
```

結果語の意味:

| 結果 | 条件 |
|---|---|
| **COMPLETE** | 全MUST Gateと受入条件を証拠付きで満たす |
| **PARTIALLY VERIFIED** | 実装は完了したが、人間の実機確認等が残る。出荷可能を意味しない |
| **BLOCKED** | DECISION、権限、環境、正本が不足し、安全に進めない |
| **FAILED** | 実装または必須検証が失敗し、既知の完了方法がない |

### 6.9 証拠Level

「確認済み」という語を一種類にしない。要求ごとに到達した証拠Levelを示す。

| Level | 証拠 | 主張できる範囲 |
|---|---|---|
| **E0 未確認** | 説明、推論、source inspectionのみ | 実装候補であることだけ |
| **E1 静的** | compile、型、lint、SAST、schema検査 | 静的制約を満たすこと |
| **E2 論理** | unit、property、state model test | 隔離したロジックが契約を満たすこと |
| **E3 結合** | 実DB、queue、filesystem、serviceとの結合試験 | 対象構成で境界が機能すること |
| **E4 システム** | 本番相当環境のE2E、移行、障害復旧、性能 | 対象環境・条件で利用シナリオが成立すること |
| **E5 人間受入** | 実画面、実機、音、操作、アクセシビリティ、業務確認 | 人間の知覚・業務期待を満たすこと |
| **E6 本番観測** | Canary、SLI/SLO、telemetry、利用者結果 | 本番利用条件で期待結果が継続していること |

上位Levelは下位Levelを自動的に代替しない。例えばE5の目視成功は、型安全性やSecurity検査を代替しない。必要Levelは要求とリスク分類から事前に決める。

最低基準:

- R0: E0と文書形式確認
- R1: E1 + E2
- R2: E1 + E2。外部I/O、永続化、並行処理、他component境界を変える場合はE3、E2E挙動、移行、性能、障害復旧を変える場合はE4、UI・音・操作を変える場合はE5も必須
- R3: R2 + 該当専門Roleから独立したSecurity/復旧証拠。段階展開可能な本番系はE6のSLIが承認済み公開条件を満たした場合だけ公開範囲を拡大

### 6.10 AIが判断に迷った場合のアルゴリズム

AIは「合理的だと思う方」を即座に実装せず、次の順に処理する。

1. 既存の承認済み要求、ADR、状態表、不変条件に明示解があるか検索する。
2. 同じ所有境界に既存実装パターンが二例以上あるか確認する。
3. 選択が外部挙動、永続化、権限、互換性、費用、安全性を変えるか判定する。
4. 変えない場合は限定的推測条件を確認し、ASSUMPTIONとして記録して進む。
5. 変える場合は選択肢、利点、危険、移行、推奨案を提示してDECISIONを待つ。
6. 回答待ちでも独立して行える調査、test設計、prototypeがあれば進める。
7. 決定後、Context Packageと受入条件を更新してから本実装する。

質問は「どうしますか」だけにせず、判断に必要な情報を揃える。ただし推奨案を示す場合も、承認済みDECISIONであるかのように扱わない。

### 6.11 決定権限

AIは提案、調査、実装、検証支援を行えるが、次の承認者にはならない。一人が複数Roleを兼務してもよいが、どのRoleとして決定したかを記録する。

| 判断 | Accountable role | AIが行えること |
|---|---|---|
| 利用者価値、優先度、対象外、受入条件 | Product owner | 選択肢、利用scenario、影響を整理する |
| コンポーネント境界、状態所有者、公開技術契約 | Tech lead / Architect | 現行構造の抽出、代替案、trade-offを提示する |
| 認証、認可、秘密、脅威受容 | Security owner | threat候補、検査、修正案を提示する |
| schema、保持、削除、移行、復元 | Data owner | 差分、移行案、dry-run、整合性testを作る |
| UI操作、文言、視覚、アクセシビリティ | UX/Product owner | mock、比較、測定、問題候補を作る |
| SLO、配備、rollback、障害対応 | Service owner / Operations | Runbook、監視、演習、影響予測を支援する |
| 試験戦略とrelease evidenceの妥当性 | QA/Test owner | case生成、実行、自動集計、gap分析を行う |
| 法務、契約、ライセンス例外 | Legal / Compliance owner | 対象箇所と確認事項を抽出する |
| R2/R3の出荷可否 | Product + relevant owners | 証拠packageを作成し、不足を報告する |

AIが生成した変更を同じAIが試験しても、自動的に独立承認とはならない。R2では少なくとも承認済み契約に基づく機械的oracleまたは別contextのレビュー、R3では該当専門Roleによる承認をMUSTとする。

### 6.12 例外手続

納期や環境制約によりSHOULDを満たせない場合、単に「今回は省略」と記録しない。例外記録には次をMUSTで含める。

```text
Exception ID:
外す規則:
理由と期限:
影響する要求・利用者・データ:
発生確率と最大影響:
代替統制:
検出方法:
復旧方法:
解消責任者:
承認者:
失効日:
```

MUSTおよびMUST NOTへの例外は、本書だけを根拠には認めない。適用法、契約、組織方針、製品risk ownerの承認に従う。期限切れ例外は自動継続せず、再評価する。

### 6.13 AI作業状態

AIの作業自体も状態機械として扱う。後続状態の進入条件を満たさないまま進めない。

| 状態 | 進入条件 | 許可される作業 | 終了条件 |
|---|---|---|---|
| **INTAKE** | 依頼を受領 | 対象、目的、成果物の整理 | 対象workspaceと要求候補を特定 |
| **CONTEXT_REVIEW** | 参照先を特定 | Context Package、コード、試験、変更中差分の読取 | FACT、UNKNOWN、正本衝突を報告 |
| **DECISION_PENDING** | 推測禁止領域にUNKNOWNあり | 調査、選択肢、prototypeのみ | Accountable roleがDECISIONを記録 |
| **CONTRACT_READY** | 要求・不変条件・合否oracle確定 | 実装計画と試験計画の提示 | リスクに応じた承認を取得 |
| **IMPLEMENTING** | Contract承認済み | 承認範囲内の編集、局所試験 | 差分と必要試験が完成 |
| **VERIFYING** | 実装差分完成 | 静的、自動、結合、実環境検証 | 必須Evidence Levelへ到達または失敗確定 |
| **HUMAN_ACCEPTANCE** | E5または専門承認が必要 | 画面・音・業務・Security等の提示 | Accountable roleが承認または差戻し |
| **COMPLETE** | 全Gate、Context更新、rollback確認 | 結果報告のみ | 新しい変更要求が発生するまで維持 |
| **BLOCKED** | 停止条件が成立 | 証拠保全、未確定事項の報告 | blocker解消後に必要な前状態へ戻る |

AIは `CONTEXT_REVIEW` を省略して既存コードを編集してはならない。R2/R3では `DECISION_PENDING` を実装で迂回してはならない。差戻し後は、変更内容に応じてCONTRACT_READYまたはIMPLEMENTINGへ戻り、失敗した試験だけでなく影響回帰を再評価する。

### 6.20 依頼を受けた直後の判定と机上例

AIは依頼文を受け取った時点で実装承認とみなさず、最初に次のいずれかへ分類する。

| 判定 | 条件 | AIの次の行動 |
|---|---|---|
| **既存契約への適合修正** | 承認済み期待値が一意で、現行挙動が違反している | riskを分類し、既存契約をoracleとして最小修正と影響回帰を行う |
| **内部実装の変更** | 外部挙動を変えず、1.5の条件をすべて満たす | ASSUMPTIONと参照patternを記録し、R1統制で進む |
| **契約の追加・変更** | 利用者挙動、data、API、権限、NFR、UX等を新たに決める | PROPOSALを作り、Accountable roleのDECISIONと契約更新を待つ |
| **正本の衝突** | 要求、試験、コード、実挙動が異なる期待値を示す | 1.3の衝突報告を行い、実装を停止する |
| **緊急封じ込め** | 進行中のS2/S3障害で、承認済みRunbookに操作がある | 影響拡大を止め、証拠を保全する。恒久修正は通常の契約・検証へ戻す |

依頼者がAccountable roleを兼ねる小規模開発でも、会話上の「よさそう」「任せる」だけを、未提示の仕様詳細まで含む承認に拡張しない。選択対象、観測可能な挙動、主要なtrade-offが明示され、誰がどのRoleとして承認したかを要求またはADRへ記録した時点でDECISIONになる。

次の机上例は、規則を抽象論のままにせず、AIが同じ入力から同じ停止・進行判断を行えるかを確認するための基準例である。

#### 例A: private関数の重複を既存helperへ統合する

- 調査で外部挙動、公開契約、永続化、並行性に影響せず、同じhelper利用が二例以上あることを確認する。
- R1と分類し、変更前後のunit/property testで同値性を確認する。
- helperへの置換が新しいtimeout、順序、例外変換を生む場合は「内部変更」の条件を外れ、再分類する。

#### 例B: 保存schemaへfieldを追加する

- 後方互換に見えても、default、旧reader、新writer、migration、rollback時の読取りが未決定ならR2のDECISION_PENDINGとする。
- Data ownerの承認後、6.18を埋め、旧新reader/writerのcontract test、実データ相当migration、途中停止・再実行、件数照合を行う。
- 「nullable fieldを足すだけ」を根拠にR1へ下げない。

#### 例C: 認可条件を変更する

- 変更行数に関係なくR3とする。既存testが変更案を支持していても、承認済みSecurity policyとthreat modelを正本にする。
- Security ownerのDECISION、権限昇格・tenant境界・deny-by-defaultの試験、監査log、段階展開、復旧手順が揃うまでCOMPLETEとしない。
- 本番障害中は承認済みkill switchで封じ込められるが、恒久的な権限変更を緊急対応の名目で固定しない。

#### 例D: UI配置と通知音を変更する

- 利用者に見えるためR2とし、AIが「一般的に使いやすい」配置や音量を決定しない。
- viewport、DPI、言語、入力方式、同時表示件数、アクセシビリティを受入条件にし、実装前mockのDECISIONと実装後E5を分ける。
- screenshotの一致だけで操作性、読取り時間、音量、遮蔽、キーボード操作をPASSにしない。

この4例で確認する欠陥classは、内部変更の過剰統制、data互換性の過小評価、Security判断の無断実装、人間知覚の自動試験による代用である。新しい依頼がどの例にも対応せず、進行・停止判断を一意に説明できない場合は、本書または製品Context Packageの欠落としてQUESTIONを作る。

## 7. 網羅的な検証観点

### 7.1 機能・状態

- 正常、境界値、空、最大、重複、不正、期限切れ
- 全状態と全遷移、禁止遷移、同時イベント、順序逆転
- 中断、取消、再開、対象消失、前提変化、フォールバック
- 冪等性、再送、重複イベント、部分成功
- 所有権、権限、グループ境界、リーダー交代

### 7.2 データ・永続化

- 作成、更新、削除、参照整合性、一意性
- クラッシュ直前・途中書込み・二重書込み
- 旧版からの移行、再起動、ロールバック、バックアップ復元
- 文字コード、時刻帯、桁、精度、大容量、破損データ
- 保存期間、削除要求、匿名化、監査証跡

### 7.3 並行・分散

- race、deadlock、starvation、lost update
- timeout、retry storm、circuit breaker、backpressure
- メッセージ重複、欠落、遅延、順序違い
- network partition、依存先遅延、clock skew
- leader failure、再選出、split-brain、資源予約解除

### 7.4 性能・規模

- 平常負荷、ピーク、急増、stress、soak、容量上限
- p50だけでなくp95/p99、最大待ち時間、ばらつき
- CPU、GPU、メモリ、I/O、ネットワーク、DB、キュー
- データ・利用者・組合せが10倍、100倍になった場合
- UI項目増加、画面縮小、低性能端末、低速回線

### 7.5 セキュリティ・プライバシー

- 認証、認可、最小権限、tenant分離
- 入力検証、injection、path traversal、deserialization
- 秘密管理、暗号化、ログ漏えい、個人情報
- 依存・ビルド・配布経路、署名、SBOM、脆弱性対応
- abuse、rate limit、DoS、不正自動化、管理機能
- R3、または外部入力がtrust boundaryを越えるR2では、脅威モデルから導いた攻撃scenarioを試験する。penetration testの担当独立性と対象範囲はSecurity ownerが決定する。

### 7.6 UI・UX・アクセシビリティ

- 代表操作だけでなく全操作経路と取消・やり直し
- 大量データ、空状態、エラー、ロード中、権限不足
- キーボード、マウス、タッチ、支援技術、色覚、コントラスト
- 解像度、DPI、文字拡大、翻訳、長い名称
- 誤操作防止、確認、undo、進捗、フィードバック
- 主観評価と画面比較を分け、実利用者で確認

### 7.7 運用・障害復旧

- 起動、停止、更新、縮退、再同期、ロールバック
- ディスク満杯、証明書期限、資格情報失効、依存先停止
- バックアップの取得ではなく実復元
- 観測基盤自体の障害とアラート欠落
- Runbookを初見担当者が実行できるか
- RTO/RPO、災害、リージョン障害、データ再構築

### 7.8 テスト自体の品質

- 試験が要求へ追跡できるか
- R2/R3のDecision Core、validation、認可、金額計算では、意図的に条件を反転・削除した際に試験が失敗することをmutation testまたは同等の欠陥注入で確認する。未対応toolchainでは代替手段と不足範囲を記録する。
- fixtureが現実的か、ケース間で汚染しないか
- flaky testを計測し、黙って再実行だけで隠していないか
- mockが実システムと乖離していないか
- 合否判定が実装詳細ではなく契約を見ているか
- 「実行できた」ではなく「正しい結果になった」を検証しているか

### 7.9 試験選択・失敗・隔離の統制

変更ごとに `要求ID -> 変更した契約・所有境界 -> 影響する不変条件・故障mode -> 必須試験層 -> test ID` の影響表を作る。AIはファイル名や過去の慣習だけから試験範囲を狭めてはならない。共有契約、schema、状態、build、runtime、依存versionを変えた場合は、その利用者側と移行経路を影響回帰へ含める。

flaky testは、同一artifact、同一fixture、同一の契約上同等な環境で、実装変更なしにPASSとFAILが発生する試験と定義する。扱いは次のとおり。

1. 最初のFAILを保持し、seed、時刻、順序、環境、logを証拠化する。
2. 再実行PASSで元のFAILを上書きせず、release判定では未解決として扱う。
3. release必須testは、原因修正または同等以上の決定的な代替証拠が得られるまでGateを通過させない。
4. 隔離する場合は、対象要求、owner、期限、利用者影響、代替統制、再有効化条件を記録する。R2/R3の唯一の検証を隔離してはならない。
5. flaky率、再発、隔離期間を測定し、期限切れ隔離を自動継続しない。

coverageは未実行箇所を探す補助情報であり、正しいoracle、要求・risk・故障mode台帳から導出した組合せ、禁止結果の検証を証明しない。coverage閾値を満たしたことだけで試験十分性を主張してはならない。

テストデータは、本番データと同じSecurity/Privacy分類に従う。匿名化は名前の置換だけで完了とせず、再識別可能性、希少値、自由記述、関連データの組合せを評価する。試験終了後の削除と、失敗証拠へ残せる情報の範囲を事前に定める。

## 10. 追加すべき設計・開発プラクティス

Morrowgearの現行プロセスは、状態遷移、実ゲーム検証、視覚評価、更新互換性の点で強い。一方、一般の量産製品へ適用するには次を追加する価値が高い。

1. **要求・試験トレーサビリティ**: 仕様変更時に影響試験を機械的に抽出する。
2. **ADR**: なぜその設計にしたか、見直す条件を残す。
3. **形式的な状態モデル**: 複雑なオーケストレーションはモデル検査または状態網羅を導入する。
4. **決定的シミュレーション**: 仮想時刻、固定乱数、障害注入で長時間・並行挙動を再現する。
5. **契約試験**: チーム・サービス間の変更を独立に検出する。
6. **property-based / mutation / fuzz試験**: 人が想定しない入力と弱いテストを見つける。
7. **Feature flagとkill switch**: 危険な機能を配備と公開に分け、即時停止する。
8. **Canaryとshadow traffic**: 全利用者へ出す前に本番特性で観測する。
9. **SLOとエラーバジェット**: 完璧主義ではなく利用者価値に沿って信頼性投資を決める。
10. **SBOM・provenance・署名**: 何から、誰が、どの工程で作った配布物かを追跡する。
11. **プライバシー・アクセシビリティ設計**: 最後の確認項目ではなく要求段階から扱う。
12. **独立した安全・セキュリティレビュー**: 高リスク変更では作者と検証者を分ける。
13. **障害演習と復元訓練**: 手順書の存在ではなく、実際に戻せることを確認する。
14. **廃止設計**: API、データ、feature flag、互換層を消す時期と移行を最初から定める。

## 11. 導入ロードマップ

### 最初の30日

- 要求テンプレート、受入条件、Definition of Doneを統一する。
- 主要な状態、データ、ID、責任者を棚卸しする。
- CIで単体・静的・依存検査を必須化する。
- AI利用の入力制限、承認境界、報告形式を決める。
- すべてのCritical要求とS2/S3故障modeについてE2Eまたは障害復旧scenarioを作り、rollback手順を対応付ける。件数は固定せず、要求・故障mode台帳から不足なく導出する。

### 31～60日

- 要求・試験トレーサビリティとADRを運用する。
- 契約、移行、並行、性能、セキュリティ試験を追加する。
- 構造化ログ、メトリクス、トレース、相関IDを導入する。
- SBOM、成果物ハッシュ、依存固定をリリースへ組み込む。
- flaky test、流出不具合、復旧時間を計測する。

### 61～90日

- Canary、Feature flag、kill switch、SLOを本番運用する。
- 障害・復元・依存停止の演習を行う。
- property-based、mutation、fuzz、長時間試験をリスク領域へ導入する。
- AI変更の品質・手戻り・費用を評価し、権限を段階調整する。
- 事後分析のaction itemを期限・責任者付きで追跡する。

### 12.2 外部一次資料との整合

- NIST SSDF 1.1は、セキュア開発を特定のSDLCへ後付けするのではなく、各SDLC実装へ統合できる高水準プラクティスとして整理している。本書の全工程へのセキュリティ統合と整合する。
- NIST AI RMF 1.0は、AI製品・サービス・システムの設計、開発、利用、評価へ信頼性を組み込むための任意利用フレームワークである。2026年8月時点では改訂作業中であり、固定的な最新版扱いには注意する。
- NIST Generative AI Profileは、生成AI固有または増幅されるリスクを、Govern、Map、Measure、Manageに沿って扱う。本書のAI権限、評価、出所、人間の監督に整合する。
- NIST SSDF、SLSA 1.2、CISAのSBOM最小要素は、ソース、ビルド、依存、配布物の追跡性とサプライチェーン管理を支持する。
- OpenTelemetryは観測可能性の主要信号としてtrace、metric、log等を扱う。本書では三つを集めるだけでなく、相関IDと利用者影響へ結び付ける。
- Google SREはSLIを定量指標、SLOをその目標として定義し、100%を前提にせずエラーバジェットをリリース判断へ利用する。本書の運用ゲートと整合する。
- Google SREの事後分析は、影響、対応、根本原因、再発防止を記録し、個人非難ではなくシステム改善を目的とする。本書の障害学習と整合する。
- OWASP ASVS 5.0.0はWebアプリの技術的セキュリティ統制を検証可能な要求として提供する。Web製品では本書の一般的セキュリティ観点をASVSの具体的要求へ展開する。
- OpenSSF Scorecardは、レビュー、branch protection、依存固定、CI、SAST、fuzzing、署名リリース等を自動確認する。これは有用な補助証拠だが、スコアだけで安全性を保証しない。
- DORAの現行5指標は開発フロー改善に有用だが、製品・サービスの文脈を保って使う必要がある。
- Semantic Versioningは公開APIの互換性を版番号に表す規約である。内部データ移行やユーザー資産保持はSemVerだけでは保証されないため、別途移行試験が必要である。

## 14. 最終原則

量産ソフト開発で最も危険なのは、AIが間違えることそのものではなく、何を証明したか分からないまま速度だけが上がることである。要求、設計、実装、試験、配布、運用を一つの証拠連鎖として扱い、AIの速度をその内側で使う。

**動いたこと、正しいこと、安全なこと、使いやすいこと、更新後も壊れないこと、運用で戻せることは、それぞれ別の証拠で確認する。**
