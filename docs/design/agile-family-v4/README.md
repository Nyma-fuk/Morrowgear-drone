## 1. 設計の中心

「民生用途を持つ、高機動・高出力の無人機」。重厚感は大きな箱や厚い装甲ではなく、荷重経路・推進機構・鋭い輪郭で表現する。左右対称が最優先。旧A/B/C案と、箱型の重機案は本案で置き換える。

必須の識別特徴は低い胴体、絞ったノーズ、埋込バイザー、露出したダクト内ブレード、短く強い脚、胴体に収まる装備。装飾の棘、不要な大型尾翼、外貼りの光る管、全面発光、機能のない厚い箱は使わない。

造形の対称性と画面上の対称性は別。モデルはローカルX=0の鏡面。文字は正読の例外を認める。旋回姿勢・外光による画面上の差は幾何の欠陥として扱わない。UIは情報と操作性を優先し、左右同じパネルを無理に並べない。

## 2. 共通規格

| 項目 | 設計値・規則 |
| --- | --- |
| 座標 | 造形正本は前=-Y、上=+Z、左右=X。ゲームへの変換は書出し境界で一度だけ適用 |
| 対称 | 全部品を片側から鏡面生成。対応頂点の反射位置誤差1e-5モデル単位以下を試作基準。法線・UV・装備原点は書出し段階でも検査 |
| 外装 | 低彩度の黒鉛色。明るいチタンは構造部に限定。機械の凹部は外装より暗くする |
| 発光 | シアン=友軍/リンク、アンバー=整備/注意、赤橙=交戦/危険、緑=完了。色だけでなく記号と文言を併用 |
| 外装分割 | 大きい主面→機能パネル→少数のラッチ。微細線を増やして質感を代用しない |
| アイコン | 正本から同じ投影・照明で生成。32pxと64pxで輪郭を確認。数字、短縮名、輝度だけに依存しない |
| サイズ | 今回の造形単位は比率。ブロック単位への縮尺、既存当たり判定、Dock接地は別の承認・検証対象。見栄えのために衝突や速度を勝手に変えない |
| 保守 | 現行ID、アイテムデータ、レシピ、役割、保存、Wing8機制約を維持。名称変更とID変更を混同しない |

## 3. 全機体

共通の低い艇体・推進部・脚を使い、役割は機構で差を付ける。試作は6ロールとも四発配置。既存の通常機からのローター数変更を含む未承認案であり、慣性・速度・音・当たり判定の変更を意味しない。四発化が過大に見える場合は承認前に二発共通機へ戻す。

| ロール | 輪郭・機構 | 下から見た識別 | 禁止 |
| --- | --- | --- | --- |
| Field | 最小の装備量。中央サービスベイと接点 | 平たい接点パネル | 万能兵装に見せる |
| Scout | 細身の背面、短い左右センサーフィン、中央レンズ | 一つの保護された調査レンズ | 片側アンテナ、軽すぎる脚 |
| Cargo | 胴体下に低く長い荷室、締結リブ | シャッターと拘束具 | 巨大な箱で機体を覆う |
| Engineer | 中央の作業レンズ、左右の収納工具レール | 作業口と保護リング | 戦闘用の赤い兵装に見せる |
| Security | 左右の埋込兵装レール、照準器 | 前向き砲口、中央照射口、対称発射筒 | 異なる兵装を左右にばらばらに付ける |
| Salvage | 中央ウインチ、広い荷物空間、強化スキッド | 巻取りドラムと収納クランプ | 短い脚で荷物が接地する |

Securityの兵装ごとの最終形は別に承認する。AUTOは取付可能範囲内で複合構成とし、表示される兵装と使用可能兵装を一致させる。モジュール1個の装着を左右の装置2個として表現する場合も、弾薬・性能が倍になると誤解させない。

正本試作は各ロールのhero/front/rear/top/bottom/left/rightと.blendを同じフォルダに出す。symmetry.jsonは頂点位置検査のみ。形状承認、アニメーション、ゲーム内当たり判定のPASSではない。

## 6. UIの共通構造

装飾的な装甲パネルを画面へ持ち込まず、機械の鋭さは境界線・記号・余白で表現する。情報量とクリック回数を優先する。暗い中性色の面、白い本文、限定的な状態色。色だけで判定させない。

初期タイポグラフィー案は本文14〜16表示px、補助12px以上。MinecraftのGUI倍率・フォント実測で確定し、縮小変換で文字を潰さない。狭い画面では列を畳み、横幅に合わせて文字を際限なく小さくしない。

### 戦術画面

- 上部: 所有者・次元・接続状態・総数。表示中フィルターと選択数を明示。
- 左側: UNIT/WING/DOCKタブ、検索、ロール/任務フィルター、安定ソート。一覧項目は永続IDで選択を保持。
- 中央: 地形・軌道・目標・作戦範囲。平常時は地図が主役。ズーム中心とパン位置を一覧更新で動かさない。
- 右側: 選択対象と命令。単機、Wing、複数Wing、全機のどれかを常時明示。実行不可は理由付き。
- 下部: 実行中の任務、割込、復帰先、停止理由。最大表示行とスクロール領域を固定。
- 狭い画面: 左右は同時に固定表示せず、どちらかを開く。地図とモーダルへの二重入力を防ぐ。

### バイザー

平常時は集約1行と近傍マーカー。中央照準、ホットバー、体力、字幕の領域を保護する。注視対象だけ詳細表示し、注視が外れた瞬間に内容を入れ替えない。固定対象は自動ピックアップとは別枠。

複数戦線は最大3件の作戦行へ集約し、追加数を表示。各行に敵数、投入数、補給/増援、重要な不足を持つ。距離だけで毎フレーム順序を変えない。作業中のWingを戦闘行へ全部置き換えない。

近傍マーカーは補間済み3D位置と同フレームの投影から配置。混雑時は機体→Wingへ集約し、リーダー線と重なり回避を使う。遮蔽・画面外・背面・古いBeaconを別表現。POWER LOSTは遠距離でも救援対象として残すが、削除済みの実体を生存表示しない。

## 7. HMI: 命令・フィードバック・音声

HMIは画面装飾ではなく、人の入力から機体の応答までを含む。共通の順序は「対象選択→意図確認→送信→受理/拒否→実行→中断/復帰→結果」。送信しただけで実行済みと言わない。

| 段階 | 視覚 | 音声 |
| --- | --- | --- |
| 選択 | 枠と対象数。ゲーム内位置と対応 | 無音 |
| 送信待ち | 保留表示。連打による二重送信を防ぐ | 無音 |
| 受理・開始 | 指示先と現任務を更新 | 選択部隊について一報「巡回開始」 |
| 割込戦闘 | 一時群と元任務を併記 | 集約して「迎撃へ移行」 |
| 補給 | 帰還理由と不足資源 | 必要時「補給へ帰還」 |
| 復帰 | 復帰先の存在を再検証して表示 | 実復帰時のみ「任務復帰」 |
| 操作失敗 | 理由・対象・代替操作を残す | 重大時だけ短く通知 |
| 電力喪失 | ビーコン、機体、距離、更新時刻 | リンクから「飛行電力喪失」 |

日本語の短い機械通信を使い、雑談や感情演技をしない。毎状態の全発話はせず、全状態を発話/集約/無音へ分類する。[通信設計](../DESIGN_RADIO_CARRIER_V2.md)の状態別表とキュー規則を継続する。音声は未作成・未承認。所有者ごとの通信チャンネル、重要のみ/OFF、独立音量、字幕、再接続時の再生抑止を必須にする。

## 8. 全アクションの演出契約

| 動作 | 表現と禁止事項 |
| --- | --- |
| 発進/着艦 | 接地・回転・離床が一致。停止中に飛行音を続けない |
| 追従/合流/巡航 | 同じ原点から連続軌跡。機体の速度を演出都合で変えない |
| 旋回/待機 | 不要な帯で視界を埋めない。状態識別は灯火とHUDで補う |
| 走査/作業/植林 | 実際の対象と時刻に合わせる。未完了ブロックを完了色にしない |
| 収集/輸送 | 回収対象から搬入先への流れ。架空のアイテムを増やさない |
| 給電 | 子機から実接点への青白ビーム。予約だけで放電しない |
| 戦闘移行 | 短いフレアと状態灯。反復進入で連続点滅させない |
| レーザー | 充填は口内、照射は橙白芯、終了は短い残光と排熱。遮蔽・目標一致を維持 |
| 機関砲 | 前方に断続曳光。連射音は機体位置、着弾音は着弾位置。不要な金属音を足さない |
| ミサイル | 発射口→安全離隔→誘導→着弾を区別 |
| 回収/牽引 | 実接続、巻上げ、荷の揺れ、最低面、引渡しに一致 |
| 電力喪失/破壊 | 推進停止、落下/残骸とBeaconの整合。生存しているか不明なら鮮度を示す |
| 格納/アイテム化 | 世界側の実体削除とアイテム生成が一致してから完了表示 |

距離に応じて詳細を減らしても、発射/充填/給電の意味を取り違えさせない。遠方で無限に太い光線へ補正しない。光、音、字幕を同一の確定イベントへ紐付ける。

## 9. 完了と移行ゲート

現在の成果は仕様と承認用の造形試作。全23アイコンや全画面を既に作成・反映したという意味ではない。

1. この仕様に対し全登録ID、全ロール、全画面、状態enumの追加漏れを確認する。
2. 共通機体と全ロールの輪郭を承認。7方向と機構の動きを確認する。
3. 同じ規格で23アイテムと設備の正本を作る。小表示、手持ち、設置、接地、進入を承認。
4. 全画面を実データと空/異常/多数条件で試作。操作ケースとHMIの受理/拒否/中断/復帰を確認。
5. 演出と音声を試聴・実ゲーム確認し、旧資産を段階的に置換。
6. 既存ワールド、サーバー/クライアント、役割混在、Wing、補給、回収、保存を回帰。変更した成果物のハッシュと実画面を対応付ける。

自動試験、対称性、見た目、操作、実ゲーム、ユーザー承認を別の判定として記録する。
