# Morrowgear サーバー性能改善・挙動互換計画

更新日: 2026-10-05  
対象: Morrowgear Drone Java Mod  
状態: Phase 1から4の主要対策を実装、机上回帰試験完了

## 1. 目的

低性能な専用サーバー、大規模な敵集団、多数のドローン、長距離任務でも、Minecraft のメインサーバー Tick を長時間占有しない構造へ変更する。

性能改善によって次を変えてはならない。

- プレイヤーが発行した命令の意味、対象、優先度
- ドローンの任務、Wing、Cohort、攻撃ウェーブ、Dock予約、補給、サルベージの継続性
- 敵の脅威評価と、プレイヤー危機を最優先する規則
- レーザー、機関砲、ミサイルの攻撃ドクトリン、編隊、資源消費、演出開始条件
- Dockが消失・満杯・再配置された場合の待機、再割当、帰還
- セーブ、再読込、チャンク再読込、プレイヤー再接続後の状態
- 複数プレイヤー間の所有権、データリンク、補給網の分離
- 既存UIに表示される状態、理由、残量、作戦情報

最適化の対象は「同じ判断を何度も計算する方法」と「一度に処理する量」であり、ゲーム上の判断規則そのものではない。

## 2. 互換性の定義

### 2.1 完全一致が必要な結果

同じワールド状態と同じプレイヤー命令に対して、次は新旧処理で一致させる。

1. 選択される任務と目標ID
2. Wing、Cohort、攻撃群の参加機と予約スロット
3. 選択されるDockと待機順位
4. 選択される兵器、発射数、資源消費
5. サービス帰還理由と再出撃条件
6. サルベージ対象、支援Engineer、搬送先Dock
7. 脅威の順位と作戦区域への必要機数
8. 状態スタックへ退避する任務と、復帰時のフォールバック

### 2.2 許容する差

- 同じ安全な経路群の中で、迂回点が数ブロック異なる
- 重い探索を複数Tickへ分割したことによる、通常1から4 Tick以内の判断遅延
- 同じ作戦結果を保ったまま、検索・通信・表示更新の周期がずれる
- 視覚品質を保ったクライアント専用の照明表現への置換

戦闘開始、手動命令、POWER LOST、飛行安全、Dock最終進入では遅延を許容しない。これらには予約した緊急処理枠を使う。

### 2.3 禁止する変化

- 処理予算不足を理由にSTANDBYへ落とす
- キャッシュ失効を任務終了として扱う
- 対象消失時に古いentity ID、Dock、座標を使い続ける
- 攻撃ウェーブ中に兵器、目標、レーザースロットを再構成する
- Dock予約の更新遅延で別機が同じ場所へ着艦する
- 省略した探索結果を「経路あり」「敵なし」と断定する

未完了の計算は `UNKNOWN/PENDING` として保持し、前回の安全な結果または現在任務を維持する。

## 3. 移行原則

### 3.1 状態機を変更する前に観測する

既存処理から、次の決定を副作用のない `Decision Snapshot` として記録する。

```text
ownerId / dimension
decisionKind
inputRevision
resultRevision
targetId / missionId / dockPos
memberIds / reservedSlots
reason
createdTick / expiresTick
```

新処理を影実行し、既存処理の結果と比較する。差異がある間は既存処理だけを採用する。

### 3.2 共有計算と個体実行を分離する

所有者・作戦単位で一度だけ計算するもの:

- 所有機一覧とWing/Cohort構成
- 敵接触情報と脅威順位
- 作戦区域、必要機数、交代要員
- Dock空き状況、予約、待機列
- 攻撃ウェーブ計画とレーザーFormation Generation
- フィールド任務の走査カーソル
- 補給網の搬送計画

各ドローンが毎Tick行うもの:

- 現在の飛行目標への姿勢・速度制御
- 直近区間の衝突回避
- 自分の資源消費と故障判定
- 受領した計画のrevision確認
- 緊急停止、POWER LOST、プレイヤー手動命令

### 3.3 世代と有効期限

共有結果には `revision` と `expiresTick` を付ける。次の変化で即時失効する。

- 対象死亡、次元移動、アンロード
- Dock破壊、所有者変更、予約変更
- プレイヤーの明示命令
- 任務ID、Wing、Cohort、攻撃ウェーブ世代の変更
- POWER LOST、重大損傷、飛行安全違反

失効後は現在の安全な行動を維持し、次の計画を待つ。古い計画を別任務へ流用しない。

## 4. 機能別の安全な改善

### 4.1 経路・衝突判定

現行の最終目的地まで0.45ブロック刻みで調べる処理を、次の三層へ分ける。

1. `Immediate Safety`: 機体前方8から12ブロックを毎Tick精密判定
2. `Local Route`: 32ブロック以内を数Tick有効な経路として生成
3. `Strategic Route`: 長距離はチャンク・高さマップ単位で粗く経由点を生成

既存の迂回候補、左右優先、上昇回避、Dock進入レーンは評価式として残す。変更するのは、全距離を一度に精密判定しない点だけとする。

互換条件:

- Dockのouter、gate、landingの進入順を維持
- 固定任務の戦略経由点を、Wingスロット移動で破棄しない
- 洞窟、屋根、巨大壁、液体、牽引物のクリアランスを維持
- 計算未完了時は直進せず、現在速度を安全に減速して任務を保持
- 手動Dock帰還は最優先のまま維持

実装では候補ごとの評価値を一度だけ計算し、ソート比較中に衝突照会を再実行しない。1機あたりの精密衝突照会へTick上限を設定する。

### 4.2 脅威ネットワーク

報告キーを `sourceId + entityId` から、所有者内の `dimension + entity UUID/ID` を中心とする統合接触へ変更する。各センサーの観測は統合接触の証拠として保持する。

```text
Contact
  target identity
  strongest threat/player danger
  latest position
  reporting sources
  firstSeen / lastSeen
  source Wing / mission
```

互換条件:

- PLAYER-GUARDが通常Scout報告より優先される
- 同じ敵を複数機が観測しても接触は一つ、観測元は失わない
- 異なる敵はすべてCombat Theaterへ渡す
- TTLと敵死亡による消去を維持
- Scoutから全所有機へのデータリンク共有を維持

整理処理はpublishごとに行わず、所有者ごとに1Tick最大1回行う。Base Defenseは接触差分だけを一定間隔で発行する。

### 4.3 Dock割り当て

個々の機体が全機体・全Dockを調べる方式から、所有者単位の `Dock Allocation Snapshot` を作る。

```text
allocationRevision
dock occupancy/reservation/service capability
request priority and queue position
drone -> dock assignment
holding sector
```

互換条件:

- 手動帰還、飛行電力、修理、弾薬・レーザー補給の優先順位を維持
- Dockが満杯なら上空待機し、任務を破棄しない
- 長時間駐機機が必要に応じて譲る規則を維持
- Dock消失後もmanualDockReturnとserviceReturnを保持
- 新しいDock出現時に再割当できる
- サルベージ機と回収機の二枠予約を原子的に扱う

予約確定だけは同一サーバーTick内で直列化する。スナップショットが古い場合は着艦せず待機し、二重予約を防ぐ。

### 4.4 Wing・Cohort・編隊

所有機一覧を1Tickに1回だけ構築し、任務別・Wing別・Cohort別の索引を作る。各機は同じ不変スナップショットを参照する。

互換条件:

- GROUP、MISSION、COHORTを統合せず、既存の意味を維持
- リーダー離脱時の権限移譲と元リーダー復帰を維持
- 欠員発生時にFormation Generationのスロットを詰め直さない
- 一時迎撃後、元任務が有効なら復帰し、終了済みなら状態スタックのフォールバックへ進む
- 充電待ちの機体を理由に、飛行可能な全機を無期限にMUSTERへ拘束しない

分離・整列計算は空間グリッドで近傍だけを参照する。見た目の機体間隔と衝突回避半径は変更しない。

### 4.5 戦闘配分と複合兵装

既存のEngagement Lease、Attack Wave、Formation Generationを性能改善の境界として使う。計画は作戦単位で一度だけ生成し、各機は実行だけを行う。

互換条件:

- 進行中ウェーブでは目標・兵器を再選択しない
- レーザー群の最大8機、固定スロット、冷却軌道、途中参加を維持
- ミサイルは確定済み最大5発のロックを斉射完了まで変更しない
- 機関砲は進入、直線掃射、離脱の攻撃軸を途中変更しない
- 残存兵器があればDockへ帰らず、ウェーブ境界で切り替える
- 交代要員と復帰機の入れ替わりを繰り返さない

敵クラスタリングは空間グリッドを使い、必要機数の結果が旧ロジックと一致することを影実行で確認する。

### 4.6 動的照明と演出

飛行中の実LIGHTブロック更新はサーバー負荷が高い。機体ライン、ローター、戦闘色、充填、軌跡の発光はクライアント描画を正本とする。

互換条件:

- 見える色、範囲、戦闘状態、POWER LOST状態を維持
- ゲーム上の照明が必要なService Dock周辺だけは低頻度の実光源を許可
- 演出省略が索敵、命中、状態判定へ影響しない

### 4.7 チャンク維持

個体ごとのチケットを、Wing、任務、サルベージ搬送、母艦単位の共有リースへ集約する。

互換条件:

- プレイヤー不在でも承認済み遠隔任務は継続
- 超長距離サルベージとルート航行を途中停止しない
- 所有者ごとの上限を超えた場合も任務を破棄せず、優先度付き待機列へ移す
- プレイヤー近傍では重複チケットを追加しない

移動後の古いチケットを早く解放する一方、牽引対象やDockだけがアンロードされないよう任務範囲を一つのリースに含める。

### 4.8 母艦、フィールド作業、爆発

ブロック操作にはサーバー全体の共有予算を使う。個々の母艦・Engineerが独立して上限まで処理しない。

互換条件:

- 採掘対象範囲、Bedrock停止、ドロップ回収、内部収納を維持
- 途中停止しても同じカーソルから再開する
- 採掘演出の段階と実ブロック消去の対応を維持
- ミサイル弾着順、遅延起爆、ダメージ、地形強度判定を維持
- 予算切れは失敗ではなく翌Tickへの継続とする

母艦の地形判定は高さマップタイルをキャッシュし、船体が新しいタイルへ進入した部分だけ更新する。

## 5. サーバー処理予算

処理量だけでなく経過時間にも上限を設ける。初期値は計測を目的とし、ゲームバランス値とは分離する。

| 区分 | 1 Tickの初期上限 | 枯渇時 |
|---|---:|---|
| 緊急飛行安全 | 予約枠、全対象 | 必ず実行 |
| 精密衝突照会 | 256回/level | 次Tickへ継続 |
| 長距離経路展開 | 64ノード/level | PENDINGを維持 |
| LivingEntity空間検索 | 16回/level | 前回接触をTTL内で利用 |
| Dock再割当 | 1 owner/level/tick | 待機高度を維持 |
| ブロック作業 | 64変更/level | カーソル保存 |
| 爆発・弾着 | 8件/level | 発射順を保って延期 |
| UIスナップショット | 1 owner/5tick | 最終revisionを表示 |

数値は仮の安全開始値である。Core i3-6100U実機の計測で、通常時p95 35ms未満、p99 45ms未満となるよう調整する。単に処理を減らすのではなく、緊急処理と通常処理を別枠にする。

処理周期は `tickCount % interval` を全機で共有せず、所有者・機体UUID・任務IDから安定した位相を生成して分散する。

## 6. 段階移行

### Phase 0: 観測のみ

- 各処理の回数、経過時間、候補数、検索距離、繰越数を計測
- 既存挙動は変更しない
- 低速Tick時だけ集約ログを出し、通常運用を汚さない

### Phase 1: 局所的な無挙動変更

- comparator内の再計算を除去
- 同一Tick・同一入力の結果を再利用
- pruneをpublish単位からowner/tick単位へ変更
- UUID位相で周期処理を分散

出力結果が完全一致するため、最初に適用できる。

### Phase 2: 共有スナップショット

- 所有機、脅威、Dock、Wing/Cohortを共有化
- 新旧を影実行し、決定差分を記録
- 差分ゼロのシナリオから新処理へ切替

### Phase 3: 予算付き経路探索

- 近距離・局所・戦略経路へ分離
- 長距離処理を複数Tick化
- 旧経路をフォールバックとして残す
- 洞窟、壁、Dock進入、牽引の順で切替

### Phase 4: 世界処理の集約

- 動的照明のクライアント化
- チャンクリース統合
- 母艦、作業、爆発の共有予算化

### Phase 5: 旧処理の撤去

30分以上の実ゲーム連続試験、低性能サーバー試験、セーブ再読込試験で差異がない処理だけ撤去する。機能フラグと旧セーブ読込は少なくとも一つの公開版の間維持する。

## 7. 必須回帰試験

### 7.1 機能試験

- 手動Dock帰還、満杯待機、Dock消失、後設置Dockへの再割当
- 補給帰還、部分補給、別兵器への切替、再出撃
- 1から4地点のルート、最寄り地点開始、Wing航行
- Scout報告、プレイヤー危機、GUARD、複数戦域への配分
- レーザー1から8機、途中参加、冷却、遮蔽、移動目標
- 機関砲CAS、ミサイル複数ロック、同時斉射
- POWER LOST、Engineer開削、サルベージ牽引、空きDockへの復旧
- Cargo連続補給、補給元変更、Dockへ毎回戻らない搬送
- 母艦移動、攻撃、1チャンク採掘、回収、取り出し

### 7.2 規模試験

| シナリオ | 最低条件 | 合格条件 |
|---|---|---|
| Dense Fleet | 64機、同一基地 | 衝突なし、p99 45ms未満 |
| Invasion | 32機、敵200体 | 全接触を保持、Watchdogなし |
| Dock Surge | 32機、Dock16基へ一斉帰還 | 二重予約なし、全機が着艦または待機 |
| Long Route | 16機、1000ブロック | Tick停止なし、任務継続 |
| Remote Salvage | 1000ブロック、遮蔽墜落 | 開削、牽引、修理、任務復帰 |
| Distributed Fleet | 4プレイヤー、各16機、別地域 | 所有権混線なし、チャンク上限内 |
| Carrier Load | 母艦4隻、移動・採掘・攻撃 | 共有予算内で継続 |
| Soak | 上記混成で30分以上 | メモリ、キャッシュ、チケットが単調増加しない |

### 7.3 決定差分試験

テストごとに新旧の次を比較する。

```text
selected target
assigned members
dock assignment and queue order
weapon and salvo
mission/task stack after interruption
resource deltas
final mode/state/reason
```

経路座標は完全一致ではなく、安全性、到着、所要時間上限、最大曲率、最低高度で比較する。

## 8. 監視指標

通常ログではなく、診断コマンドまたは性能HUDで次を確認できるようにする。

- MSPT p50/p95/p99、最大値
- Morrowgear全体と処理区分ごとの時間
- 衝突照会、entity検索、block read/write回数
- owner別のドローン、接触、Dock要求、チャンクリース数
- PENDING経路、繰越作業、期限切れスナップショット数
- キャッシュhit率と要素数
- 攻撃ウェーブ、Dock予約、サルベージ予約の競合数

診断機能は既定OFFとし、通常プレイ中にチャットや警告ログを連続出力しない。

## 9. 実装順序と中止条件

推奨順序:

1. 経路照会の計測、評価値の一回計算、距離上限
2. Threat Networkの接触統合とprune集約
3. 所有機スナップショットとDock割り当て共有化
4. Wing/Cohort、戦闘区域、センサー検索の共有化
5. 経路探索の三層化と処理予算
6. 動的照明、チャンクリース、母艦・作業予算
7. UIへ性能劣化ではなく運用状態としてPENDING/WAITINGを表示

各段階で次のいずれかが発生したら切替を中止し、旧処理へ戻す。

- 決定差分が仕様で説明できない
- 任務がSTANDBYへ脱落する
- 目標、Dock、Wing、所有者が混線する
- 攻撃ウェーブ、資源、発射が二重実行される
- 旧版セーブを読めない
- 平均値は改善してもp99または最大Tickが悪化する

## 10. 結論

既存機能を維持したまま改善できる。ただし、巨大な中央AIへ一括置換する方法は採らない。既存状態機を実行主体として残し、重複する検索と計画だけを世代付き共有スナップショットへ移す。

最も安全な第一段階は、挙動を変えない計測、候補評価の一回化、整理処理の集約、周期処理の位相分散である。その後、新旧決定の影実行で一致を証明できた領域から共有化する。

## 11. 2026-10-05 実装結果

実装済み:

- 長距離衝突照会を96ブロック以内に限定し、戦略迂回を24、48、72ブロックの区間へ分割
- 迂回候補の衝突評価を候補ごとに一度だけ実行
- 脅威報告を敵entity単位へ統合し、整理処理を所有者ごとに間引き
- level内LivingEntity走査を1 tickに1回へ集約し、その後に所有者別の敵性判定を実行
- 所有機一覧へ任務、Wing、警戒命令、3次元近傍セルの索引を追加
- Dock一覧とサルベージ搬送可能性を所有者・tick単位で共有
- Dock待機順位の算出をソートから線形比較へ変更
- 動的LIGHTブロックを参照数で管理し、機体ごとの更新位相を分散
- 同一チャンクの遠隔任務チケット更新をlevel・tick単位で重複排除
- フィールド走査を作戦全体で1 tick最大512サンプルへ制限
- 母艦の同一tick高さ照会と静止中の地形スナップショットを共有
- 戦域割当の目標別件数と戦域IDを索引化
- ミサイル同時起爆をlevelごとに1 tick最大8件へ制限し、超過分を次tickへ継続
- サービスDockの子機確認を毎tickから20 tick周期の分散実行へ変更
- 派生キャッシュを切断時・サーバー停止時に破棄
