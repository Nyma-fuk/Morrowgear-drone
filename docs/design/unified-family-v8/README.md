## 正本と派生

models内の各フォルダに同名BLENDとGLBを置く。アイテム画像は同じモデルから描画する。ドローンは前方-Y、上方+Z、対称軸X=0。モデル座標は制作単位で、Minecraftの当たり判定へ直接適用する寸法ではない。

素材はPBR材質として格納している。既存MGM形式にはアニメーション機構・黒ガラスの光学表現をそのまま渡せないため、今回のGLBをファイル名だけ変えてゲームへ上書きしない。ゲーム向け変換、描画原点、スケール、材質、可動部との接続が必要。

機体のキーは1が接地・収納、40が巡航、80が装備展開、120が復帰。これは制作確認用タイムラインであり、そのまま実ゲームの状態機械に置き換えるものではない。実行時は既存状態を入力として部品を動かす。ローター回転、Scoutの走査点、腕、扉、ウインチ、ミサイル射出のキーを保持する。

## 構造検証

全30モデルの停止状態で左右反転した頂点位置を照合。機体6種は脚の足裏より非脚部が上にあることを確認。黒いドームもこの最低面に含む。GLBを独立に読み直し、ヘッダー、埋込バッファ範囲、座標の有限性、非空メッシュ、機体アニメーションの有無を検査した。

登録アイテムと出力の対応、画像の透明度・寸法・非空、アイテム画像の完全重複がないこと、HUDのアトラス範囲と各サイズの出力も検査する。検査数はファイル内のバッファやメッシュ数で増えるため、ゲームプレイの試験ケース数ではない。

## 残る品質確認

数値検査PASSを参考画像の再現性PASSと混同しない。現時点の機体モデルは概念画より面構成とディテールが簡略で、特に外装の質感、中央胴体の連続性、収納時の装備の見え方は追加の照合対象。これを最終品質と認定していない。

全可動域の接触、格納容積、ミサイル扉からの射出順序、故障時の姿勢、実機体とのサイズ、Dock進入、手持ち向き、100機時の描画負荷は未検証。実ゲームへの差し替えは行っていない。

HUDでは16pxの複雑な役割記号は細部が弱いため、主要表示は24px以上を基本とする。16pxは補助表示に限定し、名称・状態色・選択強調と組み合わせる。記号だけで全情報を伝えようとしない。白いPNGは実行時に必要な色を乗算して使う。

## 再生成

1. Blender 5.2でtools/drone-design/blender/build_unified_family_v8.pyを実行する。全体は--all、単体は--asset securityなど。
2. PillowのあるPythonでtools/build_unified_art_catalog.pyを実行する。
3. tools/verify_unified_art.pyで書き出し結果を読み直す。

既存src/main/resourcesの資産、ワールド、配布JARをこの生成処理から変更しない。ユーザーの作業中のコード変更も保持する。
