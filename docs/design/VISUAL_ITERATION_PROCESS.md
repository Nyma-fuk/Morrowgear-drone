# 実ゲーム観察を含む開発・修正手順

2026-09-20。演出、モデル、アイコン、HUD、操作画面、飛行動作を変更する作業に適用する。

## 完了の意味

自動試験の成功、ゲーム内の機能成立、見た目の合格は別々に記録する。画像生成、ソース確認、固定状態の描画プローブだけでは通常プレイの合格としない。実画面が撮れない、現象を再現できない場合は「未確認」とし、完成扱いにしない。ユーザーが差し替えのみを指示した場合はその範囲を守り、実地確認を省略した理由を記録する。

## 反復手順

1. 承認済みのデザインと対象動作を確認し、「何が見えるべきか」「何が見えてはいけないか」をケースごとに書く。新しい意匠への変更は案を提示して承認を得る。
2. 修正前の現象を実ゲームで撮影する。JARのハッシュまたは開発ビルド識別、ワールド、位置、視点、距離、機数、任務、昼夜、解像度、GUI倍率、FOV、描画設定を記録する。欠ける条件は不明と明記する。
3. 観察とログを対応付けて原因を絞る。画面上の印象だけで飛行制御やダメージ条件を変更しない。一度に独立した原因を多数変更しない。
4. 修正と影響範囲の回帰試験を実施する。実際に起動する成果物が最新か確認する。旧ビルドのままの画面は修正後の証拠に使わない。
5. 同条件で実ゲームを撮影し、修正前・承認案と比較する。動作は連続フレームまたは動画でも観察する。停止画だけでちらつきや追従の安定性を合格にしない。
6. 不一致を個別に記録して修正し、同じケースを再実施する。回数を先に固定せず、対象ケースの不一致解消と回帰確認を終了条件とする。
7. 合格・不合格・未確認・対象外とその理由、証跡、残課題を報告する。ユーザーによる見た目の承認とAIによる技術確認は区別する。

## 観察ケース

- 距離: 8/24/48/96ブロックを基準に、通常プレイの距離を優先する。原寸画像で識別できることを確認し、拡大画像だけで合格にしない。
- 視点: 前後・左右・上下、視点移動、画面端、画面外からの再進入。機体と光源・射出口・ラベルがずれないこと。
- 光環境: 昼夜、明暗の背景、壁の手前と奥、一部遮蔽。見える部分は表示し、遮られた部分を透過表示しない。ただし承認済みのHUD透視仕様は別判定。
- 状態: 発進、巡航、合流、旋回、充填、照射、終了、冷却、帰還、着艦、電力喪失。変更対象とその前後の遷移を含める。
- 規模: 単機、3機、8機、複数Wing。多数機対応の変更では100機級も別途確認し、重なり、視界妨害、ちらつき、フレーム時間の劣化を確認する。
- 画面: 通常解像度と低解像度、GUI倍率変更。文字の可読性、情報の優先順位、切れ・重なり、操作対象の識別を確認する。

全変更で全ケースを無条件実施するのではなく、影響範囲から適用ケースを決める。除外理由を記録し、共通描画や座標変換を変更した場合は関連演出にも範囲を広げる。

## 実行上の制約

既存の検証ワールドと機体を優先し、不要な機体を増やさない。試験用機体は識別して後片付けする。通常の速度・時間進行で評価し、見栄えを良くするためにゲーム速度や攻撃条件を変えない。固定プローブは描画切り分け専用であり、通常の任務開始から終了までの確認を置き換えない。ゲームの再起動は反映に必要なときにまとめ、確認後は原則起動状態を維持する。

## ケース記録

### 2026-09-20の再発防止事項

- 深度比較は対象Minecraftバージョンの標準実装に照合する。既存テストの期待値だけを根拠にせず、壁の手前・奥・部分遮蔽を実ゲームで比較する。
- 固定プローブの対象が難易度やライフサイクルで消えていないか先に確認する。開始ログは描画成功ではない。
- クライアントとサーバーの個体年齢を共通時計として扱わない。同期イベントは共通時刻で評価し、遅延追跡・再読込を試験する。
- 試験終了後の画像を動作中の証拠にしない。画像内容とログの時刻を対応させる。

各ケースに、ID、狙い、期待表示、ビルド、環境、再現操作、実表示、証跡、判定、原因、修正内容、再確認結果を残す。未確認をPASSの件数へ含めない。ユーザーの実画面による不具合報告は、自動試験がPASSでも未解決として扱う。
